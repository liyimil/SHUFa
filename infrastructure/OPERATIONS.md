# 部署与运维手册

## 发布前门禁

1. CI 的格式、静态检查、类型检查、测试和全部生产构建通过。
2. 在 Staging 空库执行 Prisma 迁移，并使用经过权利复核的内部测试内容走通上传、裁切、双人审核和发布。
3. Android 与 iOS 真机各完成一次“拍摄—确认—查字—对比—建议—再练—分享—撤销—删除”。
4. 内容、版权、隐私、未成年人规则和结构建议阈值分别由责任人签字。
5. 镜像以 Git 提交 SHA 标记；保留上一个已验证镜像及对应数据库迁移记录。

## 生产配置

API 在 `NODE_ENV=production` 时会校验必需配置并拒绝示例 Secret。至少通过 Secret 管理服务注入：

- `DATABASE_URL`、`REDIS_URL`
- `JWT_SECRET`、`INTERNAL_WORKER_TOKEN`、`ADMIN_ACCOUNTS_JSON`
- `PUBLIC_WEB_URL`；必须是公开 Web 的 HTTP/HTTPS Origin，用于生成可访问的分享链接与结果卡地址
- `WEB_CACHE_INVALIDATION_URL`、`WEB_CACHE_INVALIDATION_TOKEN`；URL 指向公开 Web 的 `/api/internal/catalog-cache`，Token 至少 32 位且仅供 API 与 Web 使用
- `S3_REGION`、`S3_BUCKET_PRIVATE`、`S3_BUCKET_PUBLIC`
- 云厂商使用静态密钥时的 S3 凭证；支持工作负载身份时不落盘静态密钥

Web 和后台的 `NEXT_PUBLIC_API_BASE_URL` 是构建参数。生产默认不公开 Swagger；临时诊断需显式设置 `ENABLE_API_DOCS=true`，结束后关闭。

## 发布顺序

1. 备份数据库并记录当前镜像、迁移版本和对象存储版本策略。
2. 运行 `pnpm --filter @calligraphy/api prisma migrate deploy --config prisma.config.ts`。
3. 先滚动发布 AI 和 Worker，再发布 API，最后发布 Web 与后台。
4. 检查 `/api/v1/health`、AI `/health`，并用内部测试数据完成最小冒烟流程。
5. 观察错误率、队列积压、P95 延迟和对象存储错误；稳定后扩大流量。

迁移必须先在 Staging 和数据库副本验证。包含破坏性 schema 变更时采用“扩展—迁移数据—切换—收缩”，禁止把回滚寄托在直接降级数据库结构上。

## 回滚

- 应用故障：将流量切回上一提交 SHA 的镜像，保持向前兼容的数据库结构。
- Worker 故障：暂停消费者，保留 BullMQ 任务，修复后重放幂等任务。
- AI 故障：停止生成新建议；查字、手动确认和历史记录继续可用。
- 内容问题：后台下架 Glyph；API 归档并审计、删除公开衍生对象，再调用 Web 标签失效端点。重复下架可安全重试未完成的对象删除或缓存失效。
- 生产 CDN 必须配置对象删除后的 purge 或不缓存缺失的公开对象；供应商接入后用旧图片 URL 验证下架生效时间，不能只验证查字列表消失。
- 分享撤销：API 不再签发私有图片 URL。已经签出的图片 URL 最长仍可能在 5 分钟内有效，生产 CDN 不得延长该响应缓存。

## 备份与恢复演练

- PostgreSQL：每日全量备份并启用时间点恢复；每月至少在隔离环境恢复一次，记录 RPO/RTO。
- 私有对象：启用版本控制、服务端加密和生命周期策略；删除流程先撤销业务访问，再按隐私保留策略物理清理。
- 公开内容：保留源资产和不可变衍生版本；误删恢复后校验 SHA-256 与数据库对象键。
- 演练证据包含开始/结束时间、恢复点、校验结果、偏差和责任人，不以“已开启备份”替代恢复验证。

## 用户作品删除队列

1. API 在一个数据库事务中把作品置为 `DELETION_PENDING`、撤销相关分享、清除图片分析和建议衍生数据，并创建 `artwork_deletion_tasks` 记录；从此不再签发该作品的下载地址。
2. API 将删除任务写入 `artwork-deletion-v1` 队列。`ARTWORK_DELETION_DELAY_SECONDS` 控制物理清理延迟，范围为 0～2592000 秒，默认 0；生产值必须由隐私保留策略批准。
3. Worker 对私有桶执行幂等对象删除，成功后通过内部令牌回调把任务和作品置为 `COMPLETED`/`DELETED`。BullMQ 最多重试 5 次；最终失败记录为 `FAILED`，作品仍保持不可访问。
4. 用户或客户端重复删除会把失败任务以递增的 `attemptNumber` 重新排队；旧一轮成功或失败回调不能覆盖新一轮状态。
5. 对象存储启用版本控制时，`DeleteObject` 只建立删除标记；必须同时配置经合规批准的非当前版本生命周期，才能在保留期后完成底层物理清理。

值班检查 `artwork_deletion_tasks` 中持续超过保留策略窗口的 `PENDING` 和全部 `FAILED` 任务，并同时核对 BullMQ 失败队列、对象键是否仍存在以及分享链接是否已撤销。不得为了重试把作品恢复为可访问状态。

## 用户图片上传安全

- 直传地址只写入私有桶，预约上限为 10 MB、单边 256～12000 像素、总计 4000 万像素，仅允许 JPEG、PNG 和 WebP。
- `/uploads/:uploadId/complete` 不信任客户端或对象元数据中的格式和尺寸；API 有界读取对象，用文件头识别真实格式、按方向核对宽高、拒绝多帧图片并强制完成解码。
- 长度、格式、尺寸、帧数、像素预算或解码失败时，待上传记录进入不可访问状态并删除对象，不得手工跳过校验或直接补发分析任务。
- Staging 必须分别用格式伪装、截断图、超大像素图、对象覆盖和并发完成/取消验证 S3 兼容行为，并确认失败对象不存在且 BullMQ 没有对应任务。

## 图片质检失败降级

- `artwork-analysis-v1` 在最后一次重试失败后必须调用内部失败端点；API 把分析置为 `FAILED`，不得长期停留在 `PENDING`/`PROCESSING`。
- 质检技术失败不等于图片质量通过。作品只开放手动确认、查字和本地对比，创建练习、再次练习及结构建议仍要求质量状态为 `PASSED`。
- 值班时按 analysis ID 关联 Worker 失败日志与数据库终态，检查失败回调是否成功；禁止直接把失败分析改成 `PASSED`。恢复服务后由用户重新拍摄，后续若增加显式重试必须创建可审计的新一轮任务。
- 迟到的成功与失败回调都不得覆盖先到达的终态；发布前需要用 AI 503、超时、API 回调断连和重复回调验证该约束。

## 日志与告警

API 返回 `X-Request-Id`，并输出不记录查询串、请求体、令牌、签名 URL 或图片内容的完成日志；公开分享路径中的持有者令牌固定显示为 `:shareToken`。Worker 输出任务 ID 和领域对象 ID。API 与 Worker 在记录异常、持久化失败原因或发送终态失败回调前，统一脱敏 URL、Bearer/JWT、常见凭据、用户对象键、邮箱、手机号和长不透明令牌，并限制诊断文本长度。脱敏器不能作为记录请求头、请求体或查询串的理由。

生产日志平台需要按 request/job/artwork/analysis ID 建立检索，并对以下情况告警：

- API 5xx、认证失败突增、上传完成失败
- Redis 断连、队列等待时间和失败任务数
- 作品删除任务失败、超过保留窗口仍为 `PENDING`，或数据库已 `DELETED` 但对象仍存在
- AI 超时、无效输出和建议生成失败
- 对象存储 4xx/5xx、数据库连接耗尽和磁盘/备份异常

真实 Staging、TLS、告警接收人、备份恢复演练和滚动回退只有在云环境与负责人确定后才能验收。
